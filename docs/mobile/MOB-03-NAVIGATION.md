## Route contract

`src/navigation/routes.ts` exports `Destination`, `DestinationPath`, `parseResourceId`, `parsePath`, `parseLink` and `destinationPath`. Construct a resource destination only after `parseResourceId` returns a branded ID; `destinationPath({ kind: 'card', boardId, cardId })` produces the one canonical Card path `/boards/:boardId/cards/:cardId`. Board views are `/boards/:boardId/calendar` and `/boards/:boardId/table`; Workspace uses `/workspaces/:workspaceId`. The other accepted protected paths are `/home`, `/tasks`, `/boards`, `/inbox`, `/search`, `/settings` and `/invitation`. UUID syntax follows the backend's default `ParseUUIDPipe` pattern; it is not an authorization check.

Incoming links accept only `https://kanvexa.tech` and the configured `kanvexa-dev` scheme. Queries, fragments, percent encoding, whitespace, backslashes, foreign authorities, malformed IDs and unlisted paths are rejected. This intentionally conservative contract does not carry invitation or password-reset tokens; their owners must define a secure dedicated entry contract. HTTPS App/Universal Links are not established by this code; domain association remains MOB-46.

## Session and permission handoff

Following the owner's updated testing requirement, the EAS `preview` profile now sets `EXPO_PUBLIC_NAVIGATION_PREVIEW=1`. It builds the actual Kanvexa application with its usual entry point, name and package. That build opens Home and exposes only the data-free tab/Search/Settings/invitation scaffolds without creating an authenticated session. Resource routes still require a verified external session and server access. Builds without this flag retain the signed-out default. Future features must not expose private data through these preview shell routes. Device acceptance now uses the Kanvexa APK; the older gallery checks below are historical evidence only.

`SessionAdapter` supplies a stable `getSnapshot()` and `subscribe()` with the six documented session states. Snapshot objects must stay referentially stable until the state changes; `sessionKey` must be a nonempty opaque identity-generation key and must change on account replacement. `NavigationRoot` accepts an adapter and defaults to signed out. MOB-05 must connect a real verified session, keep credentials outside navigation and clear its private caches on sign-out or account change. No authenticated production session is supplied here.

Protected routes do not render while restoring, verifying, signed out, expired or offline uncertain. A validated path is retained in memory across the sign-in handoff and discarded on logout or account switch. While verification is unresolved, navigator resets do not overwrite the pending path; a newer validated warm native intent replaces it, and malformed links do not. Device delivery and multiple-link ordering still require verification. The pending path contains identifiers only and is not persisted. `ResourceBoundary` renders its children only when its `allowed` result carries the current `sessionKey` and canonical resource path; it immediately hides them for `checking`, `unavailable`, mismatched identity/path or a non-authenticated session. Feature owners must bind the result to the session and route for the request, not the state when a stale response arrives. Resource scaffolds currently report unavailable because their features are not implemented. Future owners must derive access from server authorization, handle 403/404 and revocation, and clear private cached content. The boundary itself is not a server permission check.

## Verification and limitations

The parser/session tests cover the allowlist, malformed inputs, fail-closed decisions and account changes. Simulated initial URLs and native URL events exercise Expo Router's installed linking configuration, subscription and intent handler, including rejected links and listener cleanup; they do not establish Android operating-system delivery. The guard and resource component tests exercise session transitions and removal of previously rendered private content with a test-only adapter. The router integration harness exercises route transitions with Expo Router's JavaScript tabs and test-only native-module shims, including Card syntax and unavailable states, navigation from each intended origin, Back from a cold detail and a detail resumed after authentication, and navigation to the safe fallback after an invalid warm intent. The origin test directly pushes the canonical path; it does not claim the future business screens already provide Card actions. The JavaScript harness emits `ROUTE_NAMES_CHANGED` development warnings during some navigator transitions.

On a Samsung SM-A507FN running Android 11 and Expo Go 58.0.5, the production entry displayed the signed-out scaffold. A separate gallery with a synthetic session exercised the four native tabs, selected icons, Search and Settings, dark and light themes, and hardware Back. A gallery-only bottom sheet and text field confirmed Back dismisses the keyboard, then the sheet, then the route. The screen was also temporarily set to 320 dp wide at the existing 1.1 font scale: the subtitle wraps without overlapping the tab bar. The original screen size and dark mode were restored. The gallery uses an `exp://` URL and does not prove custom-scheme or HTTPS delivery in a standalone native build, real login, server authorization, or warm/cold link ordering on a device. iOS is untested. The gallery session and overlay are test-only; the production bundle check rejects gallery sources. No MOB-04 API, MOB-05 session persistence, P2+ business screen or MOB-46 domain association is implemented here.

For an Android preview APK, check installation, launch without a crash or blank screen, the signed-out scaffold, and rejection of protected or malformed destinations. With a separate test-only authenticated adapter, check all four tabs, switching, nested Back, modal dismissal and keyboard dismissal. Real session restoration and authenticated access require MOB-05; verified HTTPS App Links require MOB-46. Never install a gallery adapter as production authentication or clear existing application data to perform these checks.
