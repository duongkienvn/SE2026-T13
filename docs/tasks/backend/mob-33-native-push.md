## API, migration and lifecycle handoff

All routes retain `/api` and the existing response/error envelope, JWT guard, strict validation, response allowlists, global HTTP rate limit and `Cache-Control: no-store`:

| Route                                                      | Contract                                                                                                                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /users/me/push-preferences`                           | `{enabled,deliveryAvailable}`; absent row means OFF                                                                                                          |
| `PATCH /users/me/push-preferences`                         | Exactly `{enabled:boolean}`; true requires channel + eligible owned device; false works with feature OFF and deactivates account devices/cancels queued work |
| `POST /users/me/push-devices`                              | Installation UUIDv4, Expo token, native platform, matching environment/project; response `{installationId,registered:true}` without routing material         |
| `GET /users/me/push-devices/current?installationId=UUIDv4` | Owned-only `{registered,eligible}`, foreign/absent installation indistinguishable                                                                            |
| `DELETE /users/me/push-devices/:installationId`            | Idempotent owned revoke, bodyless 204; durable delayed-enrollment JWT fence, not ordinary account-toggle cleanup                                             |

`NativePush1794787200000` remains additive and forward-only: separate account opt-in, encrypted registry, session-revocation fences and unique notification/device outbox. No changes to legacy notification-preference schema, auth rules or notification categories. Apply explicitly only on an authorized target with backup; startup never migrates/synchronizes. `down()` refuses: rollback application/disable delivery while retaining schema, then roll forward. Account erasure removes devices (cascading jobs), revocations and push preferences before Inbox history.

Transactional enqueue stays inside `NotificationService.record` only after a new permitted Inbox insert. No duplicate occurrence enqueue, suppressed category push or history backfill. Worker claims at most 25 jobs/cycle, two-minute leases, six send attempts/24-hour horizon, 16 receipt lookups, rate caps and bounded maintenance. Permission-backed enrollment expires no later than JWT expiry (fixed one-hour server session); inactive/stale routing material is swept after seven days. `TICKET` is not delivery; `ACCEPTED` means provider receipt acceptance, never OS display/read. `UNKNOWN` is terminal for automatic sends, including possible acceptance on disconnect/crash.

Lock/dispatch boundary: Board → live Workspace membership (or Workspace share lock for Workspace-only events) → recipient User NO KEY UPDATE → device → job. Registry takes sorted identity advisory locks, sorted User locks, then device/jobs. Account disable, transfer and ACL revocation serialize the preparation decision. HTTPS happens only after that decision commits: opt-out/revocation **cannot recall an already in-flight provider request**. Cancellation prevents a late provider result from resurrecting cancelled work; it cannot retract an OS alert already accepted by the provider. Offline logout has no immediate server-revocation claim: clear local credential/rendering, retain only cleanup IDs, revoke on a safe matching session and rely on enrollment expiry meanwhile.
