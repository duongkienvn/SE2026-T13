# Kanvexa UI

Follow [AGENTS.md](../../../AGENTS.md). Code-span paths below are relative to the repository root.

## Select the correct design context

1. Inspect the affected route, feature, API/query hooks, shared components, tokens, and tests. Check actual feature/API availability to classify controls without removing approved visual slots merely because the backend is missing.
2. Read the [base design guidelines](../../../docs/design/design-guidelines.md). For Post-MVP work, also read the relevant [blueprint](../../../docs/design/product-ux-blueprint.md) sections and [Post-MVP addendum](../../../docs/design/design-guidelines.post-mvp.md), and check the requested scope against the [roadmap](../../../docs/roadmap/post-mvp.md).
3. Select the screen's UX spec and approved image through the [visual reference register](../../../docs/design/post-mvp/visual-reference-register.md). Read/view only the relevant area. Text scope/security overrides govern conflicting image details; existing MVP visual baselines remain unless superseded. For other screens, use their approved screen-specific spec/reference.
4. Apply **VISUAL-FIRST, FUNCTIONALITY-PROGRESSIVE** by default whenever a frontend task implements an approved mockup/visual reference; the issue does not need to restate this rule. Build all approved UI components within the current issue's scope, retaining elements without backend support as disabled/Coming soon. Do not create fake backend, APIs, routes, data, or functionality, or expand into other pages/features. Read the issue's approved implementation decisions alongside the mockup/spec. This decision takes precedence over older blanket “show only implemented navigation” or “hide unsupported controls” wording for approved noninteractive visual slots; do not hide them merely because functionality is unavailable. Check and record conflicts, and resolve any remaining material ambiguity before dependent implementation. Security, permissions, accessibility, branding, and explicit exclusions remain binding.

## Complete the approved visual foundation

Build the full in-scope composition from the outset: layout, sections, navigation, header/sidebar, panels, typography, spacing, colors, icons, hierarchy, proportions, and responsive behavior. Missing functionality changes an approved slot's availability, not its visual presence. A few cosmetic edits to MVP components do not complete a V2 design. Aim for composition fidelity and approved design decisions, not absolute pixel-perfect matching.

Inventory the main reference elements and classify each before implementation:

| State                                   | Required presentation and behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AVAILABLE**                           | Integrate real supported functionality and necessary backend/API contracts. Navigation has a valid meaningful destination. Handle loading, error, permission, accessibility, and relevant interaction states.                                                                                                                                                                                                                                                                                  |
| **COMING SOON**                         | Keep the approved future slot in its designed position with muted/disabled styling and a clear Soon label, description, or tooltip accessible to keyboard and screen-reader users. No navigation, API calls, fake pages/data/callbacks/success feedback, unread counts, or shortcuts. No `href="#"`, no-op click handlers, or controls that appear usable. A tooltip must not be pointer-only; use appropriate disabled/static semantics with a discoverable status and no keyboard dead ends. |
| **EXCLUDED / FORBIDDEN / NOT APPROVED** | Do not render, including as Coming soon. This includes Pricing, Pro, Upgrade, Free Plan, billing/subscriptions, and artifacts excluded by approved text specs. A pictured control alone never approves a feature.                                                                                                                                                                                                                                                                              |

- Scope the visual shell/framework to the approved mockup **and current issue**. Functional pages/business logic require current scope or an explicit request; do not add backend/API/database work just to make the mockup appear functional. Do not copy sample people, Workspace/Board entities, notifications, avatars, or metrics into production UI.
- Keep Coming soon distinct from permission-denied/archived states. Never reveal protected names or data through placeholders, and never label unauthorized content as unfinished. Preserve the established permission UX and server enforcement.
- Keep the structure extensible so later issues can activate real features without redesigning the shell. Prefer typed/config-driven items with stable IDs, labels, icons, explicit availability, and routes only for Available items. Activate a slot only after its real destination/action and authorization behavior are verified.

Approved decision examples (consult the issue for exact scope; these do not require every frontend task to build these shells):

- [App Shell V2 (#91)](https://github.com/duongkienvn/SE2026-T13/issues/91), [shell spec](../../../docs/design/post-mvp/app-shell/ux-spec.md): complete sidebar/header composition, including Home, My Tasks, Starred, Workspaces, Search, and Notifications visual slots. Unsupported slots are disabled/Soon; preserve real Boards/account/context actions. Do not create future destination pages, fake Workspace rows, search popovers, unread badges, or shortcut behavior.
- [Account Settings V1 (#92)](https://github.com/duongkienvn/SE2026-T13/issues/92), [settings spec](../../../docs/design/post-mvp/settings-notifications/ux-spec.md): show all seven sections in order—Profile, Appearance, Notifications, Preferences, Security, Connected Accounts, Data & Privacy. Integrate Profile, Appearance, Preferences, Security, and Connected Accounts with real supported functionality in scope; Notifications and Data & Privacy remain disabled/Soon until delivered. No fake section routes/pages/forms or excluded Bio/avatar-upload/session/device/destructive controls.

## Build within the existing frontend

- Work in `apps/frontend/src/features/` for feature UI, `src/app/` for routing/providers/layout, and existing `src/components/`/`src/hooks/`/`src/lib/` for reusable behavior. Follow the [frontend architecture](../../../docs/architecture/frontend-architecture.md), checked against actual source.
- Reuse `Brand`/`BrandLogo` from `apps/frontend/src/components/Brand.tsx`, official assets, and semantic tokens in `apps/frontend/src/style.css`. Preserve logo artwork and canonical Kanvexa indigo; do not copy conflicting screenshot colors or introduce competing primitives.
- Use existing REST clients, TanStack Query keys, and mutation patterns for Available functionality. Scope private data to the session and Board; handle stale requests, optimistic rollback, realtime invalidation/resync, logout, and access revocation. If an API is missing, retain the approved visual slot as Coming soon and identify the deferred integration; do not mock success or expand backend scope.
- Support desktop, tablet, and mobile with intentional scrolling and reachable actions on short screens. Preserve the approved mobile drawer model and intentional horizontal Kanban scroll; avoid accidental page overflow.
- Use semantic controls, labels, visible focus, contrast, keyboard activation, Escape handling, focus trapping/restoration, and touch targets. Check keyboard alternatives for drag/drop where affected, reduced motion, and screen-reader announcements for important state changes.
- Cover loading, empty, error/retry, saving, disabled/permission, archived/read-only, and reconnect/conflict states relevant to Available features. Preserve separate Coming soon status for approved future slots; UI visibility never replaces server authorization.
- Support Light/Dark/System when theming is in scope or already supported by the affected flow. Use semantic tokens, system changes, accessible contrast, persisted preference where supported, and initial-render defaults without theme flash. A stored theme preference alone does not prove app-wide theme support.

## Verify behavior and appearance

1. Run focused interaction/regression tests and relevant checks using [kanvexa-verification](../kanvexa-verification/SKILL.md).
2. Audit the reference inventory as a visual parity matrix: element → Available / Coming soon / Excluded, implemented position/state, and any justified difference. Confirm every approved in-scope slot exists in the correct location, including collapsed/sidebar/drawer or section-list variants; confirm excluded artifacts are absent.
3. Inspect the real rendered UI in an available browser; capture comparable screenshots against the approved reference at the issue's required desktop/tablet/mobile viewports. Default targets are 375×812 mobile, 768×1024 tablet, 1280×800 laptop, and about 1440px desktop, plus materially affected breakpoints. Check supported light/dark/system modes, responsive proportions, keyboard/focus, screen-reader labels/status, permission/read-only, loading/error, long content, and overflow.
4. Confirm Coming soon items never navigate, call APIs, trigger feature callbacks/shortcuts, or show fake success/content; their visual and accessible status must not imply usability. Verify Available routes/actions and neighboring/shared flows still work. Compare layout/hierarchy first, then typography, spacing, color, and states. **A passing UI build or test is not proof of visual completeness.**
5. Store evidence under `docs/design/screens/implementation/` when required by the task, with task-record links following the [task index](../../../docs/tasks/README.md). Do not overwrite approved references or render mockup images as app UI.
6. Report visual completeness, real integrations versus Coming soon slots, exclusions, references/approved decisions used, deliberate deviations, actual visual/test results, and remaining risks. If browser tooling or required test data is unavailable, report visual QA as not run with the reason; do not require a particular external plugin.
